    Roadmap

    The libraries ktm needs so a production REST API or network service can be written and run without leaving the ecosystem, the way it is in Go. Each row says where it stands; the page is updated as they land.

    How they are built#

    • Protocols, formats and glue are written in ktm, from scratch.
    • Only security-critical cryptography comes from a vetted C library, mbedTLS, compiled into ktm itself: nothing ever has to be installed.
    • A stdlib library ships with ktm, as Go's standard library does. A package has its own repository and is fetched with ktm get: import "github.com/ozzenerol/ktm-xxx";.

    ktm already has: net, net.http (server, mux, middleware, static files), coro, json, yaml, csv, sql (SQLite), log, date, fs, proc, hash (SHA-256, CRC-32, FNV), str and String, vec, list, map, set, sort, reflect, signal, thread, atomic.

    Order#

    1. net.tls, crypto, base64 and hex, url, uuid: everything else builds on them.
    2. The net.http client and HTTPS, ktm-pg finished, flag, env config.
    3. Passwords, ktm-jwt, validation, migrations: a whole API with logins and a database.
    4. ktm-redis, the SQL interface, ktm-mysql, WebSocket, compress, the middleware pack.
    5. Metrics, tracing, regex, templates, toml, decimal, time zones, testing helpers.
    6. Tier 3, as people ask for it.

    When one counts as done#

    • Tests pass on Linux x86_64, Linux arm64 and macOS, and under -Memsafe, with a docs page whose examples run.
    • A protocol client is tested against the real server, in several versions, and measured against the Go equivalent.
    • A package's tests fetch it with ktm get, so every package also tests the package manager.
    • One reference application (a REST API with logins, PostgreSQL, Redis, migrations and metrics) uses Tiers 1 and 2 together and runs under load as a long test.

10. Middleware

Shelf is safe in the ways chapters 8 and 9 cover, but anyone can still try a million passwords, a browser app on another origin can't call it, and logs can't follow one request through the system. Middleware fixes all three without touching a handler.

Settings

struct Settings {
    i64 port;
    bool accessLog;
    @required u8[] databaseUrl;
    u8[] webOrigin;             /* the web app allowed to call the API from a browser */
    u8[] trustedProxies;        /* the load balancer's addresses, when there is one */
};

Settings gSettings;
SHELF_WEB_ORIGIN=http://localhost:5173

The middleware

    http.Mux mux;
    if (gSettings.trustedProxies.len) { middleware.realIp(&mux, gSettings.trustedProxies); }
    middleware.requestId(&mux);
    if (gSettings.webOrigin.len) {
        middleware.CorsOptions cors;
        cors.origins = gSettings.webOrigin;
        cors.expose = "X-Request-Id";
        middleware.cors(&mux, &cors);
    }
    middleware.rateLimit(&mux, 300, 60);            /* any client: 300 requests a minute */

    mux.handle("POST /users", &signup);
    http.Mux *logins = mux.group("/sessions");
    middleware.rateLimit(logins, 5, 60);            /* guessing passwords: 5 tries a minute */
    logins.handle("POST", &login);
    http.Mux *session = mux.group("/sessions");
    middleware.bearer(session, &checkToken);
    session.handle("DELETE", &logout);
  • Real IP comes first, so the rest see the client and not the load balancer. It only believes X-Forwarded-For from the proxies you name: anyone else could write anything in it.
  • Request IDs: each request gets one (or keeps the client's X-Request-Id), sent back in the reply. Put it in your log lines and a user's bug report leads straight to them.
  • CORS tells browsers which other sites' pages may call the API. A browser asks first with an OPTIONS request, which the middleware answers itself.
  • Rate limits are per client address. The whole API allows 300 requests a minute; logging in, 5. The login limit is a group of its own on /sessions, next to the group for logging out: two groups may share a prefix, each with its own routes and middleware.

Everything else stays: a handler that throws is still a logged 500, and the access log still writes one line per request (HTTP middleware lists what each one does).

Try it

$ for i in 1 2 3 4 5 6; do curl -s -o /dev/null -w "%{http_code} " -X POST localhost:8080/sessions \
      -d '{"email": "ada@example.com", "password": "guess"}'; done
401 401 401 401 401 429

$ curl -i -X POST localhost:8080/sessions -d '{}'
HTTP/1.1 429 Too Many Requests
RateLimit-Limit: 5
RateLimit-Remaining: 0
Retry-After: 12
...

$ curl -i -X OPTIONS localhost:8080/bookmarks -H 'Origin: http://localhost:5173' \
       -H 'Access-Control-Request-Method: POST' -H 'Access-Control-Request-Headers: authorization, content-type'
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: http://localhost:5173
Access-Control-Allow-Methods: GET, POST, PUT, PATCH, DELETE, HEAD
Access-Control-Allow-Headers: authorization, content-type
Access-Control-Max-Age: 600

$ curl -i -H 'X-Request-Id: trace-42' localhost:8080/bookmarks
HTTP/1.1 401 Unauthorized
X-Request-Id: trace-42
...

A 429 reply carries both limits' RateLimit-* headers, the API's and the login's; the stricter one answered.

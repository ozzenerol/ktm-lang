Building libraries

ktm -lib compiles code once into a static and a shared library, so programs that use it don't recompile it.

A module as a library

Given the geo module from Modules:

$ ktm -lib geo geo
$ ls -a geo
.  ..  .ktmlib  helpers.ktm  libgeo.a  libgeo.so  shapes.ktm
$ ktm main.ktm -o shapes && ./shapes        # main.ktm does import geo;
25
  • ktm -lib name dir writes libname.a, its shared object and a .ktmlib file into dir.
  • A program importing the module then reads only its declarations (the sources stay, as headers would) and links the library: the archive when compiled, the shared object in the JIT.
  • A module's globals that run code are set by its init function, called once before the program's own globals: imports first.
  • Generics are kept as source: each program makes the instances it uses.

Several modules in one library

When dir isn't the module name's own directory, every module under it is built into one library:

$ ls mylib
geo/  util/  web/http/
$ ktm -lib mylib mylib              # mylib/libmylib.a, each module gets a .ktmlib
  • mylib/web/http is the module web.http.
  • Files at the top of dir, and a prelude directory there, are not built.
  • A .ktmlib names its library relative to itself, so a built tree can be moved.
  • -v prints the commands that build it.

Where modules are found

An import is looked for next to the main file, then in the standard library, then in each directory of KTM_PATH:

export KTM_PATH=$HOME/ktm-libs:/opt/team/ktm
ktm main.ktm -o app

A library for C-style use

Code that isn't a module can be built into a library and installed next to the standard one:

ktm -lib mylib --install-dir=$HOME/.local mylib.ktm

Mark what it exports pub. To use it, declare its functions (and its globals with extern) in a .ktmh header you #include, and add #link <mylib>:

// mylib.ktmh
i64 mylibVersion();
extern i64 mylibCount;
#link

For ktm code, a module is simpler: no header to keep in step.

    Database migrations

    Keep a database's schema in numbered SQL files and let your program bring any database up to date with ktm-migrate. This guide builds a small notes program on SQLite, step by step: the first migrations, status, going back, migrating at start-up, changes SQLite can't make with ALTER TABLE, failures, tests and migrations built into the binary. Then the same program on PostgreSQL, several instances starting at once, migrations from merged branches, and a driver of your own.

    What you need

    • ktm 0.24 or newer. ktm-migrate v0.1.1 needs it.
    • For SQLite, a ktm built with SQLite. The sql module, which the SQLite driver uses, is only in a ktm built from source with --sqlite. The release zips don't have it. You need sqlite3 and its headers (libsqlite3-dev on Debian and Ubuntu; macOS has them):
    git clone https://github.com/ozzenerol/ktm-lang && cd ktm-lang
./build.sh --sqlite --install
    • For PostgreSQL, any ktm. The driver uses the ktm-pg package. The PostgreSQL section starts from here too.

    On a ktm without SQLite, importing the SQLite driver stops the build with this message:

    Error: ktm-migrate/sqlite needs ktm built with SQLite (./build.sh --sqlite)

    How it works

    • A migration is a version number, a name, an up script that makes a change and, optionally, a down script that undoes it.
    • The database keeps the versions that ran in a table, schema_migrations (version, name, applied_at). The runner creates it the first time.
    • up runs every migration the table doesn't have, in version order. A database that is already up to date gets nothing. The same program can migrate an empty database or last month's.
    • Each migration runs in a transaction together with its row in schema_migrations. It happens whole or not at all.
    • A lock keeps two instances of a program that start together from both migrating.

    The first migrations

    Migrations go in a directory of their own, migrations/. Make two: a table of notes and a table of tags.

    notes/
  ktm.mod
  ktm.sum
  main.ktm
  migrations/
    001_create_notes.up.sql
    001_create_notes.down.sql
    002_create_tags.up.sql
    002_create_tags.down.sql

    migrations/001_create_notes.up.sql:

    CREATE TABLE notes (
    id    INTEGER PRIMARY KEY,
    title TEXT NOT NULL,
    body  TEXT NOT NULL DEFAULT ''
);

    migrations/001_create_notes.down.sql:

    DROP TABLE notes;

    migrations/002_create_tags.up.sql has two statements. A script can hold any number of them, and they all run in the migration's transaction:

    CREATE TABLE tags (
    note_id INTEGER NOT NULL REFERENCES notes (id) ON DELETE CASCADE,
    tag     TEXT NOT NULL,
    PRIMARY KEY (note_id, tag)
);
CREATE INDEX tags_by_tag ON tags (tag);

    migrations/002_create_tags.down.sql undoes them in reverse order:

    DROP INDEX tags_by_tag;
DROP TABLE tags;

    Naming the files

    • A file is NNN_name.up.sql or NNN_name.down.sql.
    • NNN is the version: a whole number from 1, with any number of digits. 001, 42 and 20261014120000 all work. Leading zeros only keep ls in order: 001 and 1 are both version 1.
    • The name is letters, digits, _ and -. A version has one name.
    • Every version needs an up file. The down file is optional, but without it that migration can't be reverted.
    • Files that don't end in .sql, such as a README.md, are left alone. A .sql file named some other way is an error, so a typo doesn't get skipped without a word.

    Apply them

    main.ktm opens the database, loads the directory and runs everything pending:

    import "github.com/ozzenerol/ktm-migrate";
import "github.com/ozzenerol/ktm-migrate/sqlite";
import sql;

i32 main() {
    sql.Db *db = sql.open("notes.db");
    if (!db) {
        printf("can't open notes.db\n");
        return 1;
    }
    defer sql.close(db);

    migrate.Migrations ms = migrate.load("migrations");
    defer ms.free();
    migrate.Driver d = sqlite.driver(db);
    i64 n = ms.up(&d);
    printf("%d migration(s) applied, version %d\n", n, migrate.version(&d));
    return 0;
}
    ktm build
./notes
    2 migration(s) applied, version 2
    ./notes
    0 migration(s) applied, version 2
    • migrate.load(dir) reads every migration in dir, sorted by version. The path is relative to the directory the program runs in, so run it from the project, or build the migrations into the binary.
    • sqlite.driver(db) makes a migrate.Driver: what the runner uses to talk to the database. The database stays yours, so close it yourself, after the last migration call.
    • ms.up(&d) returns how many migrations ran. The second run has nothing to do.
    • migrate.version(&d) is the newest applied version, 0 for an empty database.
    • ms.free() frees what load read.

    The sqlite3 shell shows what happened:

    sqlite3 notes.db 'SELECT * FROM schema_migrations'
    1|create_notes|2026-10-16 01:58:02
2|create_tags|2026-10-16 01:58:02

    See where a database is

    ms.status(&d) lists every migration and whether the database has it. This main.ktm applies what is pending, then prints the list:

    import "github.com/ozzenerol/ktm-migrate";
import "github.com/ozzenerol/ktm-migrate/sqlite";
import sql, vec;

i32 main() {
    sql.Db *db = sql.open("notes.db");
    if (!db) {
        printf("can't open notes.db\n");
        return 1;
    }
    defer sql.close(db);

    migrate.Migrations ms = migrate.load("migrations");
    defer ms.free();
    migrate.Driver d = sqlite.driver(db);
    i64 n = ms.up(&d);
    printf("%d migration(s) applied, version %d\n", n, migrate.version(&d));

    vec.Vec<migrate.Status> st = ms.status(&d);
    defer st.free();
    for (auto s : st) {
        printf("%4d  %-8s %.*s\n", s.version, s.applied ? "applied" : "pending", s.name.len, s.name.ptr);
    }
    return 0;
}
    ktm build
./notes
    2 migration(s) applied, version 2
   1  applied  create_notes
   2  applied  create_tags
    ./notes
    0 migration(s) applied, version 2
   1  applied  create_notes
   2  applied  create_tags
    • ms.status(&d) returns a vec.Vec<migrate.Status> with version, name and applied for each migration. The vector is yours to free. The names are views of ms, so free ms after you are done with them.
    • A migration the database doesn't have yet shows as pending.

    Going back

    Three more calls move a database the other way. This main.ktm goes through all of them on the same two migrations:

    import "github.com/ozzenerol/ktm-migrate";
import "github.com/ozzenerol/ktm-migrate/sqlite";
import sql;

i32 main() {
    sql.Db *db = sql.open("notes.db");
    if (!db) {
        printf("can't open notes.db\n");
        return 1;
    }
    defer sql.close(db);

    migrate.Migrations ms = migrate.load("migrations");
    defer ms.free();
    migrate.Driver d = sqlite.driver(db);

    i64 n = ms.up(&d);
    printf("up:      %d ran, version %d\n", n, migrate.version(&d));
    n = ms.down(&d);
    printf("down:    %d ran, version %d\n", n, migrate.version(&d));
    n = ms.to(&d, 2);
    printf("to 2:    %d ran, version %d\n", n, migrate.version(&d));
    n = ms.to(&d, 0);
    printf("to 0:    %d ran, version %d\n", n, migrate.version(&d));
    n = ms.up(&d);
    printf("up:      %d ran, version %d\n", n, migrate.version(&d));
    n = ms.down(&d, 5);
    printf("down 5:  %d ran, version %d\n", n, migrate.version(&d));
    try {
        ms.to(&d, 7);
    } catch (Error e) {
        printf("to 7:    %s\n", e.message);
    }
    return 0;
}
    ktm build
rm -f notes.db
./notes
    up:      2 ran, version 2
down:    1 ran, version 1
to 2:    1 ran, version 2
to 0:    2 ran, version 0
up:      2 ran, version 2
down 5:  2 ran, version 0
to 7:    migrate: there is no migration 7
    • ms.down(&d) reverts the newest applied migration. ms.down(&d, n) reverts the newest n, newest first, and stops early when nothing is left: down 5 on two migrations reverts two.
    • ms.to(&d, version) goes up or down until version is the newest applied. to 0 reverts everything. A version that isn't a migration is an error.
    • Every call returns how many migrations ran.
    • Every call throws migrate.ERR_MIGRATE when something goes wrong, and so does load. The message names the file and says what the database said. When a migration fails shows what the messages look like.
    • A down script throws away what its up script made. Reverting create_tags drops the tags, with every row in that table. Going back is for development and for undoing a bad deploy, and it costs data.

    Migrating at start-up

    The usual place to migrate is when the program starts, before it does anything else. A new build that needs a new column then brings it along. Add a third migration, a pinned flag on notes.

    migrations/003_add_pinned.up.sql:

    ALTER TABLE notes ADD COLUMN pinned INTEGER NOT NULL DEFAULT 0;

    migrations/003_add_pinned.down.sql:

    ALTER TABLE notes DROP COLUMN pinned;

    DROP COLUMN needs SQLite 3.35 (2021) or newer.

    Now main.ktm is a program that uses the database. It migrates first, then lists the notes, pinned ones first:

    import "github.com/ozzenerol/ktm-migrate";
import "github.com/ozzenerol/ktm-migrate/sqlite";
import sql;

/* Brings the database up to date: false when a migration failed */
bool migrateDb(sql.Db *db) {
    try {
        migrate.Migrations ms = migrate.load("migrations");
        defer ms.free();
        migrate.Driver d = sqlite.driver(db);
        i64 n = ms.up(&d);
        if (n) {
            printf("%d migration(s) applied, version %d\n", n, migrate.version(&d));
        }
    } catch (Error e) {
        printf("%s\n", e.message);
        return false;
    }
    return true;
}

void listNotes(sql.Db *db) {
    sql.Row row;
    if (!sql.select(db, &row, "SELECT id, pinned, title FROM notes ORDER BY pinned DESC, id")) {
        printf("%s\n", sql.sqlite3_errmsg(db.conn));
        return;
    }
    while (sql.next(&row)) {
        printf("%3d %s %.*s\n", row.col[0].intVal, row.col[1].intVal ? "*" : " ",
               row.col[2].str.len, row.col[2].str.ptr);
    }
}

i32 main() {
    sql.Db *db = sql.open("notes.db");
    if (!db) {
        printf("can't open notes.db\n");
        return 1;
    }
    defer sql.close(db);
    sql.exec(db, "PRAGMA foreign_keys = ON");

    if (!migrateDb(db)) {
        return 1;
    }
    listNotes(db);
    return 0;
}

    migrateDb prints only when something ran, so a normal start is quiet. When a migration fails the program stops, instead of running against a schema it doesn't expect.

    ktm build
./notes
    3 migration(s) applied, version 3
    sqlite3 notes.db "INSERT INTO notes (title) VALUES ('buy milk'), ('call ann'), ('fix the bike')"
./notes
      1   buy milk
  2   call ann
  3   fix the bike

    The last section left the database at version 0, so the first start applied all three. A copy of the program whose database is at version 2 applies only add_pinned on its next start.

    • Migrate before anything else touches the database: before a server listens, before workers start.
    • ms.up only does work when something is pending. On an up-to-date database it costs one query.
    • SQLite checks foreign keys (ON DELETE CASCADE on tags) only when the connection turns them on, so main runs PRAGMA foreign_keys = ON after opening. The setting belongs to the connection, not the file.

    Changes SQLite can't make with ALTER TABLE

    SQLite's ALTER TABLE can add, rename and drop columns, but it can't add a CHECK or a foreign key to an existing table, or change a column's type. For those, SQLite's own instructions are to build a new table, copy the rows over, drop the old one and rename the new one. While that runs, foreign keys have to be off, or dropping notes would delete every tag through ON DELETE CASCADE. But PRAGMA foreign_keys does nothing inside a transaction, and every migration runs inside one.

    A script whose first line is -- migrate: no-transaction runs without the runner's transaction. This one turns foreign keys off, then opens its own transaction.

    migrations/004_title_limit.up.sql:

    -- migrate: no-transaction
-- SQLite can't add a CHECK to an existing table: build a new one and copy
-- the rows. Foreign keys must be off while the old table is dropped, and
-- that PRAGMA does nothing inside a transaction, so this script runs its own.
PRAGMA foreign_keys = OFF;
BEGIN;
CREATE TABLE notes_new (
    id     INTEGER PRIMARY KEY,
    title  TEXT NOT NULL CHECK (length(title) <= 200),
    body   TEXT NOT NULL DEFAULT '',
    pinned INTEGER NOT NULL DEFAULT 0
);
INSERT INTO notes_new (id, title, body, pinned) SELECT id, title, body, pinned FROM notes;
DROP TABLE notes;
ALTER TABLE notes_new RENAME TO notes;
PRAGMA foreign_key_check;
COMMIT;
PRAGMA foreign_keys = ON;

    migrations/004_title_limit.down.sql does the same, without the CHECK:

    -- migrate: no-transaction
PRAGMA foreign_keys = OFF;
BEGIN;
CREATE TABLE notes_new (
    id     INTEGER PRIMARY KEY,
    title  TEXT NOT NULL,
    body   TEXT NOT NULL DEFAULT '',
    pinned INTEGER NOT NULL DEFAULT 0
);
INSERT INTO notes_new (id, title, body, pinned) SELECT id, title, body, pinned FROM notes;
DROP TABLE notes;
ALTER TABLE notes_new RENAME TO notes;
PRAGMA foreign_key_check;
COMMIT;
PRAGMA foreign_keys = ON;
    sqlite3 notes.db "UPDATE notes SET pinned = 1 WHERE id = 2"
sqlite3 notes.db "INSERT INTO tags VALUES (2, 'family')"
./notes
    1 migration(s) applied, version 4
  2 * call ann
  1   buy milk
  3   fix the bike
    sqlite3 notes.db "SELECT * FROM tags"
    2|family
    sqlite3 notes.db "INSERT INTO notes (title) VALUES ('$(printf 'x%.0s' $(seq 1 201))')"
    Error: stepping, CHECK constraint failed: length(title) <= 200 (19)

    The notes, the pin and the tag survived: with foreign keys on, DROP TABLE notes would have deleted every tag. The new table has the limit.

    • The marker must be the first line of the script, exactly -- migrate: no-transaction (whitespace around it doesn't matter).
    • Without the runner's transaction, the script and its row in schema_migrations are no longer one step. Give the script its own BEGIN and COMMIT whenever it can have them, as this one does.
    • When a no-transaction script fails, the error ends in (it ran without a transaction: what ran before the error stays). Here everything after BEGIN is undone when the program closes the database without a COMMIT. The migration stays pending, so it can run again once the data is fixed.

    When a migration fails

    A migration that fails is rolled back, the error names its file, and the migrations before it stay applied. Here is a migration with a typo, notebook for notebooks:

    migrations/005_add_notebooks.up.sql:

    CREATE TABLE notebooks (id INTEGER PRIMARY KEY, name TEXT NOT NULL);
ALTER TABLE notes ADD COLUMN notebook_id INTEGER REFERENCES notebook (id);
INSERT INTO notebook (name) VALUES ('inbox');
    ./notes
    migrate: 5_add_notebooks.up.sql: no such table: notebook
    sqlite3 notes.db "SELECT version, name FROM schema_migrations"
    1|create_notes
2|create_tags
3|add_pinned
4|title_limit
    sqlite3 notes.db "SELECT name FROM sqlite_master WHERE name = 'notebooks'"

    The last query prints nothing. Version 5 isn't recorded, and the notebooks table its first statement made is gone too, since the whole migration was one transaction. The program stopped before listing anything. Fix the file and start it again. The file name in the message is built from the version number, so 005_add_notebooks shows as 5_add_notebooks.

    To act on the failure in code, catch the error and look at its code:

    try {
    ms.up(&d);
} catch (Error e) {
    if (e.code == migrate.ERR_MIGRATE) {
        printf("the database is not ready: %s\n", e.message);
        return 1;
    }
    throw(e);
}

    load checks the files before anything runs, and throws migrate.ERR_MIGRATE too:

    ProblemMessage
    a .sql file with another kind of namemigrate: 5-oops.up.sql: name it NNN_name.up.sql or NNN_name.down.sql (NNN a number, the name letters, digits, _ and -)
    a version with two namesmigrate: version 3 is add_pinned and other: one name per version
    a down file without its up filemigrate: 6_x.down.sql has no 6_x.up.sql
    the directory isn't theremigrate: can't read the directory migrations

    And the runner refuses what it can't do:

    ProblemMessage
    down over a migration without a down filemigrate: 4_index_titles has no down migration
    to a version that isn't a migrationmigrate: there is no migration 7

    Testing migrations

    A down script that nobody runs is a down script that doesn't work. A test can run every migration up, all the way down and up again, on an empty database in memory. Put it next to main.ktm, in migrations_test.ktm:

    import "github.com/ozzenerol/ktm-migrate";
import "github.com/ozzenerol/ktm-migrate/sqlite";
import sql, testing;

/* Every migration goes up, all the way down and up again, on a fresh
 * database in memory */
void testMigrationsRoundTrip(testing.T *t) {
    sql.Db *db = sql.open(":memory:");
    defer sql.close(db);
    migrate.Migrations ms = migrate.load("migrations");
    defer ms.free();
    migrate.Driver d = sqlite.driver(db);

    i64 all = ms.items.len;
    t.equal(ms.up(&d), all);
    t.equal(ms.to(&d, 0), all);
    t.equal(migrate.version(&d), 0);
    t.equal(ms.up(&d), all);
}
    ktm test
    ok  	.	0.00s  (1 passed)
    ktm test -jit -Memsafe
    ok  	.	0.00s  (1 passed)

    ms.items is the vec.Vec<migrate.Migration> that load filled, so ms.items.len is how many there are. A down script with a mistake fails the test and names the file:

    --- FAIL: testMigrationsRoundTrip (0.00s)
    migrate.ktm:275: threw 1835466753: migrate: 2_create_tags.down.sql: no such table: tagz
FAIL

    A migration without a down file makes to(&d, 0) throw, so this test also catches a missing one. A migration that should never be reverted needs a test of its own that stops above it.

    Migrations built into the binary

    load reads files at run time, so the binary needs its migrations/ directory next to it. To ship one file instead, add the migrations in code with ms.add(version, name, up, down). The texts are copied, so they can come from anywhere.

    import "github.com/ozzenerol/ktm-migrate";
import "github.com/ozzenerol/ktm-migrate/sqlite";
import sql;

/* The schema, built into the binary: nothing to ship next to it */
void schema(migrate.Migrations *ms) {
    ms.add(1, "create_notes",
           "CREATE TABLE notes (\n"
           "    id    INTEGER PRIMARY KEY,\n"
           "    title TEXT NOT NULL,\n"
           "    body  TEXT NOT NULL DEFAULT ''\n"
           ");\n",
           "DROP TABLE notes;\n");
    ms.add(2, "create_tags",
           "CREATE TABLE tags (\n"
           "    note_id INTEGER NOT NULL REFERENCES notes (id) ON DELETE CASCADE,\n"
           "    tag     TEXT NOT NULL,\n"
           "    PRIMARY KEY (note_id, tag)\n"
           ");\n"
           "CREATE INDEX tags_by_tag ON tags (tag);\n",
           "DROP INDEX tags_by_tag;\n"
           "DROP TABLE tags;\n");
    ms.add(3, "add_pinned",
           "ALTER TABLE notes ADD COLUMN pinned INTEGER NOT NULL DEFAULT 0;\n",
           "ALTER TABLE notes DROP COLUMN pinned;\n");
}

i32 main() {
    sql.Db *db = sql.open(":memory:");
    defer sql.close(db);
    migrate.Migrations ms;
    defer ms.free();
    schema(&ms);
    migrate.Driver d = sqlite.driver(db);
    printf("%d migration(s) applied, version %d\n", ms.up(&d), migrate.version(&d));
    return 0;
}
    ktm run .
    3 migration(s) applied, version 3
    • ms.add may be called in any order; the migrations are kept sorted by version.
    • The down script may be left out (ms.add(4, "seed", "INSERT ...")), and so may an empty one. That migration then can't be reverted.
    • ms.add throws migrate.ERR_MIGRATE for a version below 1, a name with other characters, or a version that is already there.
    • A migrate.Migrations declared like this starts empty. Free it with ms.free() the same way.
    • The -- migrate: no-transaction marker works the same in code.

    PostgreSQL

    The same program on PostgreSQL needs ktm-pg too, since main imports it directly. It works on any ktm; SQLite isn't needed.

    mkdir notes && cd notes

    ktm.mod now requires both packages:

    module example.com/me/notes

	github.com/ozzenerol/ktm-migrate v0.1.1
	github.com/ozzenerol/ktm-pg v0.2.1
)

    Migrations are written in the database's own SQL, so they are written again for Postgres.

    migrations/001_create_notes.up.sql:

    CREATE TABLE notes (
    id         bigserial PRIMARY KEY,
    title      text NOT NULL,
    body       text NOT NULL DEFAULT '',
    created_at timestamptz NOT NULL DEFAULT now()
);

    migrations/001_create_notes.down.sql:

    DROP TABLE notes;

    migrations/002_create_tags.up.sql:

    CREATE TABLE tags (
    note_id bigint NOT NULL REFERENCES notes (id) ON DELETE CASCADE,
    tag     text NOT NULL,
    PRIMARY KEY (note_id, tag)
);

    migrations/002_create_tags.down.sql:

    DROP TABLE tags;

    Postgres can make changes to a table in a transaction, which SQLite can't. An index on a big table is the exception. A plain CREATE INDEX blocks writes to the table until it finishes, and CREATE INDEX CONCURRENTLY doesn't, but Postgres refuses to run it inside a transaction. That is what -- migrate: no-transaction is for.

    migrations/003_index_tags.up.sql:

    -- migrate: no-transaction
CREATE INDEX CONCURRENTLY IF NOT EXISTS tags_by_tag ON tags (tag);

    migrations/003_index_tags.down.sql:

    -- migrate: no-transaction
DROP INDEX CONCURRENTLY IF EXISTS tags_by_tag;

    Without a transaction, a failed CREATE INDEX CONCURRENTLY isn't rolled back: it leaves an invalid index named tags_by_tag behind, and IF NOT EXISTS would then skip it on the next run. After such a failure, DROP INDEX tags_by_tag before running the migration again.

    main.ktm connects with ktm-pg, makes the driver with postgres.driver(c), applies what is pending and prints the status:

    import "github.com/ozzenerol/ktm-pg";
import "github.com/ozzenerol/ktm-migrate";
import "github.com/ozzenerol/ktm-migrate/postgres";
import vec;

i32 main() {
    try {
        pg.Conn *c = pg.connect();      /* PGHOST, PGUSER, ... or a URL */
        defer c.close();
        migrate.Migrations ms = migrate.load("migrations");
        defer ms.free();
        migrate.Driver d = postgres.driver(c);
        i64 n = ms.up(&d);
        printf("%d migration(s) applied, version %d\n", n, migrate.version(&d));

        vec.Vec<migrate.Status> st = ms.status(&d);
        defer st.free();
        for (auto s : st) {
            printf("%4d  %-8s %.*s\n", s.version, s.applied ? "applied" : "pending", s.name.len, s.name.ptr);
        }
    } catch (Error e) {
        printf("%s\n", e.message);
        return 1;
    }
    return 0;
}

    pg.connect() with no URL takes the server from PGHOST, PGPORT, PGUSER, PGPASSWORD and PGDATABASE. A URL works too: pg.connect("postgres://ann:secret@localhost:5432/notes"). It throws when it can't connect, so it goes inside the try.

    With a pool

    A server usually has a pg.Pool, not one connection. postgres.driverPool(pool) takes one connection from the pool for each call (up, down, to, status, version) and gives it back when the call ends, after a failure too. Two lines of main change, the rest stays:

    import "github.com/ozzenerol/ktm-pg";
import "github.com/ozzenerol/ktm-migrate";
import "github.com/ozzenerol/ktm-migrate/postgres";
import vec;

i32 main() {
    try {
        pg.Pool *pool = pg.open();
        defer pool.close();
        migrate.Migrations ms = migrate.load("migrations");
        defer ms.free();
        migrate.Driver d = postgres.driverPool(pool);
        i64 n = ms.up(&d);
        printf("%d migration(s) applied, version %d\n", n, migrate.version(&d));

        vec.Vec<migrate.Status> st = ms.status(&d);
        defer st.free();
        for (auto s : st) {
            printf("%4d  %-8s %.*s\n", s.version, s.applied ? "applied" : "pending", s.name.len, s.name.ptr);
        }
    } catch (Error e) {
        printf("%s\n", e.message);
        return 1;
    }
    return 0;
}

    In a server, run ms.up(&d) on the pool before it starts taking requests, and keep using the same pool afterwards. Either way, the connection or the pool stays yours to close.

    Several instances at once

    Two copies of a program that start together, such as two containers of one service, must not both apply the same migration. Each driver has a lock for that:

    • SQLite: each migration starts with BEGIN IMMEDIATE, which takes the database file's write lock. A second program waits for it, up to 10 seconds (the driver sets busy_timeout to 10000), then finds the migration already applied and skips it.
    • PostgreSQL: the runner holds pg_advisory_lock(postgres.LOCK_KEY) for the whole call, so the instances take turns. The later ones find nothing left to do.
    • Inside each migration's transaction, the runner checks again whether the migration is applied. A migration never runs twice.

    Two copies of the start-up program from Migrating at start-up, started together on a new SQLite file, with a migration that takes a few seconds:

    ./notes & ./notes
    4 migration(s) applied, version 4

    One applied all four. The other waited for the lock, found nothing left, and printed nothing.

    On PostgreSQL there is a catch in ktm-migrate v0.1.1. When the pending migrations include a CREATE INDEX CONCURRENTLY, two instances that start together deadlock. CREATE INDEX CONCURRENTLY waits for every open transaction to end, including the other instance's query that is waiting for the lock. Postgres breaks the deadlock by failing the waiting instance:

    deadlock detected (SQLSTATE 40P01); detail: Process 106 waits for ExclusiveLock on advisory lock [5,27508,1835886951,1]; blocked by process 105.

    The first instance finishes the migrations. The failed one finds nothing to do when it starts again. Until this is fixed, deploy a concurrent index build with one instance, or run the migrations as a step of their own before the instances start.

    Branches and merged migrations

    Two people on two branches can each add a migration. Numbering them 003 on both sides clashes when the branches merge: load refuses a version with two names. Versions made from the time (YYYYMMDDHHMMSS) don't clash:

    migrations/
  20261001090000_create_a.up.sql
  20261002090000_create_b.up.sql     from the branch merged last
  20261003090000_create_c.up.sql

    up applies every migration the database doesn't have, including one whose version is lower than the newest applied. With the program from See where a database is, before and after the merge brings create_b in:

    ./notes
    2 migration(s) applied, version 20261003090000
20261001090000  applied  create_a
20261003090000  applied  create_c
    ./notes
    1 migration(s) applied, version 20261003090000
20261001090000  applied  create_a
20261002090000  applied  create_b
20261003090000  applied  create_c

    The other way round, a database can have a version this build doesn't know, because a newer build ran it. status lists it with an empty name:

    ./notes
    0 migration(s) applied, version 5
   1  applied  create_notes
   2  applied  create_tags
   3  applied  add_pinned
   4  applied  title_limit
   5  applied

    down and to refuse to go past it, with migrate: version 5 is applied, but there is no migration 5 here.

    up leaves such a version alone, so an older build still starts against a newer database.

    A driver of your own

    Any SQL engine can use the runner through a migrate.Driver: four functions and a few fields.

    migrate.Driver d;
d.ctx = myDb;                // yours: a connection, a database, a pool
d.exec = &myExec;            // void myExec(migrate.Driver *d, u8[] script): runs a script of statements
d.queryInts = &myQueryInts;  // void myQueryInts(migrate.Driver *d, u8[] sql, vec.Vec<i64> *out): the first column of each row
d.lock = &myLock;            // void myLock(migrate.Driver *d), or null: called when a call starts
d.unlock = &myUnlock;        // and when it ends, after a failure too
d.begin = "BEGIN";           // the statement that starts a transaction ("" is BEGIN)
    • Each function gets the Driver, and throws on an error. The runner adds the file name to the message.
    • d.ctx and d.conn are for the driver. A driver over a pool sets d.conn in lock to the connection it took, uses it in exec and queryInts, and gives it back in unlock.
    • The runner only sends CREATE TABLE IF NOT EXISTS, SELECT, INSERT, DELETE, the begin statement, COMMIT, ROLLBACK and the migrations' scripts. An engine that runs those works.

    A driver can also wrap another one. This one prints every statement the runner sends, then hands it to the SQLite driver, which its ctx points to:

    import "github.com/ozzenerol/ktm-migrate";
import "github.com/ozzenerol/ktm-migrate/sqlite";
import sql, str, vec;

/* A Driver that prints every statement the runner sends, then hands it
 * to another Driver (ctx points to it) */
void logExec(migrate.Driver *d, u8[] script) {
    migrate.Driver *inner = d.ctx;
    u8[] s = str.trim(script);
    printf("exec  %.*s\n", s.len, s.ptr);
    inner.exec(inner, script);
}

void logQueryInts(migrate.Driver *d, u8[] query, vec.Vec<i64> *out) {
    migrate.Driver *inner = d.ctx;
    printf("query %.*s\n", query.len, query.ptr);
    inner.queryInts(inner, query, out);
}

void logLock(migrate.Driver *d) {
    migrate.Driver *inner = d.ctx;
    printf("lock\n");
    if (inner.lock) { inner.lock(inner); }
}

void logUnlock(migrate.Driver *d) {
    migrate.Driver *inner = d.ctx;
    printf("unlock\n");
    if (inner.unlock) { inner.unlock(inner); }
}

migrate.Driver logged(migrate.Driver *inner) {
    migrate.Driver d;
    d.ctx = inner;
    d.exec = &logExec;
    d.queryInts = &logQueryInts;
    d.lock = &logLock;
    d.unlock = &logUnlock;
    d.begin = inner.begin;
    return d;
}

i32 main() {
    sql.Db *db = sql.open(":memory:");
    defer sql.close(db);
    migrate.Migrations ms;
    defer ms.free();
    ms.add(1, "create_notes", "CREATE TABLE notes (id INTEGER PRIMARY KEY, title TEXT NOT NULL);",
           "DROP TABLE notes;");

    migrate.Driver inner = sqlite.driver(db);
    migrate.Driver d = logged(&inner);
    ms.up(&d);
    return 0;
}
    ktm run .
    lock
exec  CREATE TABLE IF NOT EXISTS schema_migrations (version bigint PRIMARY KEY, name text NOT NULL, applied_at timestamp NOT NULL DEFAULT CURRENT_TIMESTAMP)
query SELECT version FROM schema_migrations ORDER BY version

query SELECT version FROM schema_migrations WHERE version = 1
exec  CREATE TABLE notes (id INTEGER PRIMARY KEY, title TEXT NOT NULL);
exec  INSERT INTO schema_migrations (version, name) VALUES (1, 'create_notes')

    That is everything a call of up does: take the lock, make the table, read what ran, and then for each pending migration, begin, check again, run the script, record it and commit.

    Rules of thumb

    • Never change a migration that has run anywhere. The runner records versions, not the scripts' contents, so it won't notice: the databases that ran the old text keep it. Add a new migration that makes the change.
    • One change per migration, with a name that says what it does. A small migration is easy to revert and its error is easy to read.
    • Write the down script with the up script, and run the round-trip test, so down works when you need it.
    • Data is part of the schema too. A migration can INSERT or UPDATE rows (filling a new column from an old one), in the same transaction as the change that needs them.
    • **Keep schema_migrations to the runner.** Change it by hand only to repair a database, and then with the program stopped.
    • Run migrations from one place: at start-up, or as a step of the deploy before the new build starts. Not both.
